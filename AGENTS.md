# Agent Guidelines and Codebase Knowledge

## Project Overview
omaconf is an Arch Linux security hardening, debloat, and theming automation suite for Omarchy. It manages system-level hardening, security daemon configurations, package debloating, and per-theme desktop folder color integration using pure native Bash automation and standard Unix system utilities.

## Repository Architecture
The repository codebase is organized into distinct functional paths. The provisioning pipeline `scripts/setup.sh` runs as root to apply all system hardening, pacman debloating, and security configurations, delegating to discrete scripts under `scripts/lib/modules/`. The verification runner `scripts/verify.sh` performs automated assertion checks on kernel sysctl parameters, PAM configurations, firewall rules, and active security services. The modular test suite located in `tests/` executes exhaustive assertion suites spanning syntax integrity, desktop services, lockscreen regression prevention, kernel sysctl parameters, authentication controls, firewall rules, package debloating, security tooling, hardware power policies, modular pipeline architecture, and idempotency safety via `tests/run-all.sh`. Continuous Integration is configured under `.github/workflows/ci.yml` executing shell linting and multi-job matrix test suites. The legacy compatibility suite is in `scripts/test-omarchy-compat.sh`. Logging is managed by `scripts/run-setup.sh` and interactive execution is supported by `scripts/launch.sh`. Desktop theming integration is implemented in `hooks/theme-set.d/folder-color` (folder colors), `hooks/theme-set.d/shell-icons` (icon family), `hooks/theme-set.d/cli-theme` (CLI colors). Persistence hooks live in `hooks/pre-refresh-pacman.d/99-omaconf-persist` and `hooks/post-update.d/99-omaconf-persist`, and the post-update hook runs as root. Editor and tool configuration modules are located in `conf/<app>/`, and theme preview assets are located in `theme-previews/`. The root `Makefile` provides standard targets for setup, keyring selection, verification, testing, hook installation, theme sync, and editor configuration installation. Operational runbooks reside in `.skills/`. Internationalization is provided by the pure Bash dictionary engine `scripts/lib/i18n.sh`, the offline timezone-to-locale resolver `scripts/lib/locale-map.sh`, the localized `make help` renderer `scripts/lib/help.sh`, the hook bootstrap shim `scripts/lib/i18n-boot.sh`, and the translation catalogs under `scripts/lib/messages/`. The uniform preview normalization and the overlay store are owned by `scripts/lib/theme-preview.sh`, consumed by both `scripts/lib/modules/30-theming.sh` and the post-update hook. The shared user-scope installer patterns are owned by `scripts/lib/userconf.sh`, which every `conf/*/install.sh` must use instead of reimplementing backups or shell block replacement.

## Module Ownership and Boundaries
Stage modules under `scripts/lib/modules/` are loaded by `scripts/setup.sh` in a fixed order and are individually idempotent. Because every module is sourced rather than executed, a module must never call `exit`; it must use `return` to skip its own work. `00-env.sh` owns the environment and defines `user_as`, `aur_verified_install` and `omarchy_as`; every module that needs to act inside a real user session must call `user_as` for arbitrary commands and `omarchy_as` instead of invoking `omarchy` directly, so the user runtime directory and D-Bus bus are forwarded. `10-debloat.sh` owns package removal and the pin list, `20-defaults.sh` owns the browser, editor, media player and file manager defaults including the single canonical `inode/directory` entry, using Nautilus for graphical file management and GTK file dialogs without full KDE or GNOME desktop stacks, `25-desktop-cleanup.sh` owns orphan launcher entry hygiene across system, Omarchy and per-user application directories plus the pacman removal hook, `30-theming.sh` owns per-home hook installation and `62-keyring.sh` owns the GNOME Keyring Secret Service backend with Seahorse, and `32-omaqt.sh` and `35-shell-plugins.sh` own the optional desktop stack and shell plugin layer. Neovim packages are retired in `10-debloat.sh`. `32-omaqt.sh` is opt-in and no-ops with a log line unless `OMAQT_URL` is exported, so no upstream URL is hardcoded anywhere in the repository. Hardening, power, cleanup, AI removal and gaze protection stages must never be reached from the debloat stages.

## Internationalization and Locale
Supported languages are `it`, `en`, `fr`, `de`, `es`, and `pt`. Scripts never hardcode user-facing English: every human-readable message is referenced by a symbolic key resolved through `t`, `log`, `warn`, and `err` from `scripts/lib/i18n.sh`, with English always loaded first as the fallback catalog. Catalogs are plain `key=value` files and must declare exactly the same key set and the same `%s` placeholder count across all six languages. The active language is resolved from `OMACONF_LANG`, then `LANGUAGE`, `LC_ALL`, `LC_MESSAGES`, `LANG`, and finally `/etc/locale.conf`; any unsupported value falls back to `en`. `i18n.sh` and `locale-map.sh` are sourced libraries and must never alter the calling shell's options. `scripts/lib/i18n-boot.sh` is the self-contained bootstrap used by hooks and installers, which degrades to a minimal English stub when no catalog runtime is reachable. The module `scripts/lib/modules/05-locale.sh` derives the target locale, console keymap, and XKB layout from the system timezone through `resolve_target_locale`, `resolve_target_keymap`, and `resolve_target_xkb`, then persists them in `/etc/locale.conf`, `/etc/vconsole.conf`, `/etc/profile.d/omaconf-locale.sh`, and the managed Hyprland `kb_layout` block, never hardcoding an `en_US` default. The `make lang` target lists the supported languages and marks the active one.

## Operational Commands
Workflow targets are exposed through the root Makefile. The `make setup` command invokes `sudo bash scripts/setup.sh` to execute full system hardening. The `make verify` command invokes `bash scripts/verify.sh` to validate applied security assertions. The `make test` command invokes `bash tests/run-all.sh` to run the comprehensive modular test suite. The `make hook` command copies `hooks/theme-set.d/*` into `~/.config/omarchy/hooks/theme-set.d/` with executable permissions. The `make icons` command triggers immediate color synchronization for the active theme. The `make theme` command synchronizes both folder icons and Zed editor themes. The `make zed`, `make cli` commands (or `make editors` for all of them) install the corresponding configuration module. The `make clean` command removes previous setup logs. The `make lang` command lists the supported languages and marks the active one, while `make i18n-status` reports the resolved language, catalog path, and message count.

## Change Application Policy
Every system or session state change must be staged in the repository configuration first and applied exclusively through the privileged pipeline (`make setup`, which runs `pkexec bash scripts/setup.sh`). Agents must never hot-apply fixes directly to the live system: no manual `systemctl` start, stop, restart, mask or unmask, no manual copies into `~/.config`, `/etc` or `/run`, and no direct service manipulation outside the pipeline. Read-only diagnosis (`systemctl status`, `journalctl`, `busctl`, config inspection) is always allowed. Running the pipeline is the only actuation path, and it reconciles live state from the repository idempotently.

## Kernel Hardening Configuration
Kernel sysctl parameters are persisted in `/etc/sysctl.d/99-security.conf`. Memory protections include `kernel.randomize_va_space = 2`, `kernel.kptr_restrict = 2`, `kernel.dmesg_restrict = 1`, `kernel.perf_event_paranoid = 3`, `kernel.unprivileged_bpf_disabled = 1`, `kernel.yama.ptrace_scope = 1`, and `kernel.sysrq = 16`. Filesystem security includes `fs.suid_dumpable = 0`, `fs.protected_hardlinks = 1`, `fs.protected_symlinks = 1`, `fs.protected_fifos = 2`, and `fs.protected_regular = 2`. Network stack hardening includes `net.ipv4.conf.all.rp_filter = 1`, `net.ipv4.conf.all.accept_redirects = 0`, `net.ipv4.conf.all.send_redirects = 0`, `net.ipv4.conf.all.accept_source_route = 0`, `net.ipv4.icmp_echo_ignore_broadcasts = 1`, `net.ipv4.tcp_syncookies = 1`, and `net.ipv4.tcp_rfc1337 = 1`.

## Authentication and PAM Policies
Authentication security is enforced through `/etc/security/faillock.conf` which locks accounts for 900 seconds following 5 consecutive failed attempts. Password complexity rules are enforced in `/etc/security/pwquality.conf`. Access lists are controlled in `/etc/security/access.conf` and core dumps are disabled globally via `/etc/security/limits.d/99-no-core.conf`.

## Firewall and Service Isolation
The UFW firewall operates with default deny incoming and default allow outgoing policies, enabled at boot via `ufw.service`. SSH is hardened in `/etc/ssh/sshd_config.d/hardened.conf` disabling root login and password authentication while enforcing modern ciphers. Sandboxing drop-in `/etc/systemd/system/sshd.service.d/hardened.conf` applies `ProtectSystem=strict`, `ProtectHome=yes`, and `NoNewPrivileges=yes`. Unneeded daemons such as `avahi-daemon.service` and `cups.service` are disabled. Security services including `ufw.service`, `auditd.service`, `fail2ban.service`, and `usbguard.service` are enabled. NetworkManager is preserved without creating conflicting configuration overrides.

## Security Tooling Stack
Host security tools include `lynis` for system audits, `rkhunter` for rootkit scanning, `clamav` for virus scanning, `auditd` for audit logging, `usbguard` for USB authorization, `fail2ban` for intrusion deterrence, and `apparmor` with mandatory access control profiles for `sshd`, `useradd`, `curl`, and `wget`. Automated weekly security audit execution is scheduled in `/etc/cron.weekly/security-audit.sh`.

## Package Debloating and Theming
Debloated packages include `chromium`, `system-config-printer`, `thunar`, `thunar-archive-plugin`, `tumbler`, `totem`, `evince`, `eog`, `yaru-icon-theme`, `dolphin`, `okular`, `gwenview`, `xdg-desktop-portal-kde`, `plasma-integration`, `breeze`, `breeze-gtk`, `haruna`, `docker`, `docker-compose`, `gnome-disk-utility`, `gnome-themes-extra`, `sushi`, `gtksourceview4`, `gst-plugin-gtk`, `zathura`, `zathura-pdf-mupdf`, `kdenlive`, `obs-studio`, `libreoffice-fresh`, and `obsidian`. Retained and provisioned packages include `brave-origin-bin`, `slack-desktop`, `discord`, `nautilus`, `gvfs`, `gvfs-mtp`, `file-roller`, `zed`, `onlyoffice-bin`, `papers`, `loupe`, `celluloid`, `baobab`, `resources`, `7zip`, `mpv`, `trash-cli`, `podman`, `podman-compose`, `podman-docker`, `slirp4netns`, `herdr`, `gum`, `capitaine-cursors`, and `qogir-icon-theme`. Debloated packages are persisted inside `IgnorePkg` in `/etc/pacman.conf` to block accidental reinstallation. Brave Origin is the default browser and Zed is the default editor for files and projects; OnlyOffice handles office documents. Desktop theming uses `qogir-icon-theme` variants (Qogir for light themes, Qogir-Dark otherwise) and the `capitaine-cursors` non-GNOME cursor theme, applied per user through gsettings, the Qt `xdgdesktop` platform theme, and Hyprland environment hints. Each user-facing function has one application. Celluloid requires mpv as its backend, whose separate launcher is hidden. Micro, imv, MuPDF, gdu and btop are retired while preserving personal configurations. Theme previews must all be normalized to a uniform geometry, an alpha-capable ImageMagick color type, depth 8 and density 72 through `scripts/lib/theme-preview.sh`, and `theme-previews/rebuild-previews.sh` must capture the entire themed desktop including background and shell using the real canvas geometry instead of hardcoded pixel offsets. The normalization must be idempotent, must preserve the stock asset for restore, and must re-run from the root-owned post-update hook so it survives `pacman -Syu`. Never hardcode a theme name in production code: pass the themes explicitly.

## GTK and Keyring Defaults

Brave, Slack and Discord are explicit user-requested Chromium or Electron apps and may require GTK runtime libraries. Nautilus is the graphical file manager with GVFS and native archive integration. Papers handles PDFs, Loupe handles images, Celluloid handles media, Baobab analyzes disk usage and Resources monitors the system. GTK provides file selection and app chooser dialogs; Hyprland handles ScreenCast and Screenshot. GTK applications are allowed at the user's request; Thunar is retired; preserve its personal configuration. The installed Omarchy package requires gnome-keyring, which currently brings GTK3 through gcr; other required Omarchy-adjacent components retain GTK4 dependencies. Audit reverse dependencies before changing that base. `scripts/lib/modules/62-keyring.sh` provisions GNOME Keyring and Seahorse, restores optional PAM unlock at login, and retires KeePassXC while preserving personal databases. `make keyring` reconciles that integration through setup.

## Hardware and Battery Power Management
Battery longevity is enforced via a perpetual 75% charging threshold policy configured in `/etc/omaconf/power.conf`. Multi-layered persistence guarantees enforcement across boots, kernel updates, hotplugs, and suspend/resume cycles through udev rules in `/etc/udev/rules.d/98-battery-charge-threshold.rules`, systemd-tmpfiles drop-in `/etc/tmpfiles.d/battery-charge-threshold.conf`, and systemd service `battery-charge-threshold.service`. Universal sysfs targeting applies to all existing and future batteries (`BAT*`, `BATT*`). Enforcement is capability-probed, never assumed: `scripts/lib/set-battery-charge-limit.sh` is the single authority, it writes a threshold only through an interface whose read-back is a real integer, verifies the value actually stuck, and records the outcome in `/run/omaconf/battery-charge-limit.state`. `scripts/verify.sh` derives its verdict from that state through `--query`, fails when a supported interface drifted from the policy, and skips explicitly when the machine firmware exposes no charge threshold interface at all, which must never be reported as an enforced limit.

## Regression Prevention and Safety
System hardening and package debloating must strictly avoid breaking desktop functionality and user workflow. Core services including D-Bus session bus, Polkit authorization (`polkit.service`), PipeWire/WirePlumber audio (`pipewire.service`), NetworkManager, and display managers (`gdm`, `sddm`, `greetd`, `lightdm`) must never be blocked or deprived of necessary permissions. Hardening must strictly prevent double lockscreen occurrences and frozen or fake blank screen overlays by enforcing a single canonical screen locker per session, proper PAM authentication integration, non-conflicting idle/sleep triggers, and unblocked HID input devices in USBGuard. All modifications must be verified against `scripts/test-omarchy-compat.sh` and `scripts/verify.sh`.

## Single Source Rules
Every rule has exactly one home. Do not copy scripts, modules, tests, runbooks or catalogs into sibling directories: the root `scripts/`, `hooks/`, `tests/`, `conf/`, `theme-previews/` and `.skills/` are the only canonical locations. App-specific configuration lives directly under `conf/<app>/`. Each project stores its own stage modules in `<project>/scripts/lib/modules/`; shared stages stay in the root `scripts/lib/modules/` and are sourced by consumers. `.agents/skills` is always a symlink to `.skills`.

## Skills
Operational runbooks live in `.skills/` and every skill in that directory is normative for agents working on this repository: `apparmor-management` manages AppArmor profile enforcement and auditing, `arch-hardening` owns kernel sysctl, UFW, PAM and battery policy procedures, `code-cleanup` bans decorative comments, banner echoes, emoji and dead output code, `conventional-commits` enforces the commit message format, `editor-configurations` owns Zed, Micro and Brave configuration standards, `fail-fast-first-failing` bans silent failures and unhandled suppressions, `idempotent-bash-automation` defines safe idempotent Bash and verification patterns, `desktop-applications` governs graphical application selection, GTK integration and dependency auditing, `omarchy-theming` owns theme hooks and folder color propagation, `purist` governs minimal, secure and consistent changes, `regression-prevention` guards desktop services and the single screen locker invariant, `security-audit-tooling` owns auditd, fail2ban, USBGuard, ClamAV and Lynis procedures, `system-debloat-cleanup` owns webapp shortcut and package cleanup, and `systemd-sandboxing` owns service isolation directives. Register every new skill in this inventory in the same change that creates it.

## Commit Conventions
All commit messages must follow the Conventional Commits standard formatted strictly as `<type>: <description>` or `<type>(<scope>): <description>`. The colon `:` following the target type is the only allowed punctuation or symbol. Titles must never contain emojis, exclamation marks, or extra punctuation.

## Scripting Rules and Constraints
Scripts must use strict execution modes `set -euo pipefail` in pure native Bash without Python dependencies. Never use `|| true` to suppress failures; use `|| warn "message"` for non-critical steps that can fail gracefully. Do not add comments to Makefile or hook scripts. Do not hardcode user paths; derive directories from `$HOME` or `/home/*`. All operations must run in the foreground without `systemd-run`. All modifications to `scripts/setup.sh` and `scripts/verify.sh` must remain strictly idempotent.

## Mandatory Skill Loading and Pull Requests

At the start of every task, read every `.skills/*/SKILL.md` into the agent context. This inventory must contain every local skill; update it in the same change whenever a skill is created, renamed or removed. Subproject agents inherit this rule from the root AGENTS.md.

Treat `main` as read-only. All changes, including maintenance and GitHub policy changes, originate on a feature branch and enter `main` through a pull request. Never push directly to `main`, force push it, or rewrite its published history. Published commits remain historical facts; corrections and reversions also require pull requests.

The canonical GitHub ruleset is `.github/main-ruleset.json`: no bypass actors, no branch creation or deletion, no force pushes, signed commits, linear history, squash-only pull requests, no mandatory approvals, stale approval dismissal, no additional latest push approval, resolved review threads, and successful CI and SAST checks against the latest base. Do not enable the blanket update restriction: without bypass actors it also blocks legitimate PR merges. Apply repository settings with the GitHub API and verify the active ruleset after applying it.

## Graphical Theme Integration

`24-user-configurations.sh` discovers all `conf/*/install.sh` after package provisioning and applies them through `user_as`. Brave Origin uses its native flags config and existing profile directory. Never replace active browser profile databases or preferences with static repository files.

The GTK hook owns GTK and libadwaita palette propagation and supersedes upstream Adwaita settings after each theme switch. Materia supplies the GTK base; the generated Qogir overlay uses the exact theme accent. Dark mode is the first setup default, while later explicit theme choices remain authoritative. Yazi is retired; preserve its personal configuration but remove managed launchers, hooks and shell helpers. Preview regeneration applies each actual system theme and captures the complete monitor with shell, wallpaper and sample apps, then restores the original theme, background and workspace on every exit path.
